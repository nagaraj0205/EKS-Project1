PART 0

Understand this one thing first

10 min

Almost every student gets confused at the same place, so let's kill it before you start. Two different things talk to AWS in this project, and only one of them is keyless.

  1. Fork the repository into your own GitHub account

    You need a repo you control, because you will be adding secrets and an environment to it.

    git clone https://github.com/<YOUR-USERNAME>/eks-demo.git
cd eks-demo

    You should see: the folders src/, k8s/ and .github/workflows/ci.yml.

  2. Install the six tools and prove each one works

    Do not skip the version check. Half of all "it doesn't work" problems are an old CLI.

    git --version              # any recent version
node -v                    # must be v20 or newer
docker --version           # and Docker Desktop must be RUNNING
aws --version              # must say aws-cli/2.x — v1 will not work
kubectl version --client
eksctl version

    You should see: a version number from all six, no "command not found".

  3. Give your laptop access to AWS

    This is the amber path in the diagram. It is for you, not for the pipeline.

    # Best: short-lived credentials through IAM Identity Center
aws configure sso

# Acceptable for a personal learning account:
aws configure               # paste an access key, region ap-south-1

    You should see: aws sts get-caller-identity prints your account and user.

    Never: commit these credentials, paste them into GitHub secrets, or put them in the repo. They live only in ~/.aws/ on your machine.

  4. Save your account ID in a shell variable

    You will paste it into four different commands. Set it once.

    ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
echo $ACCOUNT_ID           # 12 digits

# Windows PowerShell:
# $ACCOUNT_ID = aws sts get-caller-identity --query Account --output text

    You should see: a 12-digit number, not an error.

PART 1

Get it running on your laptop

20 min

No AWS yet. Prove the app builds and the container works locally — debugging on your own machine is a hundred times faster than debugging in a pipeline.

  1. Install dependencies with npm ci

    ci, not install. It installs the exact versions in the lockfile and fails if they disagree — the same thing CI does.

    npm ci

    You should see: "added NNN packages" and a node_modules/ folder.

  2. Start the dev server

    Confirms the app itself is fine before you blame anything else.

    npm run dev                # http://localhost:5173

    You should see: the login screen in your browser. Login will fail — there is no backend running. That is expected.

  3. Run the exact three checks CI will run

    Every red pipeline you avoid here saves you five minutes of waiting.

    npm run lint               # must be ZERO warnings, not just zero errors
npm run test:coverage      # tests + writes coverage/lcov.info
npm run build              # produces dist/

    You should see: all three finish with exit code 0 and a dist/ folder appears.

  4. Build the real container image

    This is the identical Dockerfile the pipeline uses. If it fails here, it fails there.

    docker build -t frontend:local .

    You should see: both stages complete and docker images lists frontend:local at roughly 50–80 MB.

  5. Run it and check the two endpoints that matter

    Kubernetes will judge this container on /healthz, and your app will be configured by runtime-config.js. Look at both now so you recognise them later.

    docker run --rm -p 3000:3000 \
  -e API_BASE_URL=http://localhost:8080 \
  -e APP_ENV=dev \
  frontend:local

# in a second terminal:
curl -i http://localhost:3000/healthz
curl -s http://localhost:3000/runtime-config.js

    You should see: HTTP/1.1 200 with the body ok, and a JS file containing the API_BASE_URL you passed in.

    Understand this: you changed the app's configuration without rebuilding the image. That is the whole point of the design — one image, many environments.

PART 2

Build the AWS side

45 min — mostly waiting
Money starts here

From step 2.2 onwards you are being billed by the hour. Roughly $0.20 per hour, about $5 per day. Read Part 6 now so you know how to switch it off, and finish the whole guide in one sitting if you can.

  1. Create the ECR repository

    The private warehouse your images get pushed to. Name it exactly this, or change ECR_REPO in ci.yml to match.

    aws ecr create-repository \
  --repository-name ai-interview-dev-platform/frontend \
  --region ap-south-1 \
  --image-scanning-configuration scanOnPush=true

    You should see: JSON containing a repositoryUri that starts with your account ID.

  2. Create the EKS cluster

    This is the slow one. Start it, then read the reference doc while it runs.

    eksctl create cluster \
  --name ai-interview \
  --region ap-south-1 \
  --nodegroup-name workers \
  --node-type t3.small \
  --nodes 2 \
  --managed \
  --vpc-nat-mode Disable      # saves ~$40/month; fine for learning

    You should see: "EKS cluster is ready" after 15–20 minutes. Do not interrupt it.

    Don't confuse these: eksctl creates an OIDC provider for the cluster (so pods can assume roles). That is a completely different thing from the GitHub OIDC provider you create in step 2.4. You need both, for different reasons.

  3. Connect kubectl and create the namespace

    The pipeline deploys into demo. It will not create it for you.

    aws eks update-kubeconfig --region ap-south-1 --name ai-interview
kubectl get nodes
kubectl create namespace demo

    You should see: two nodes with status Ready, then namespace/demo created.

  4. Register GitHub as an identity provider

    This tells AWS "tokens signed by GitHub are worth reading". Once per AWS account, ever.

    aws iam create-open-id-connect-provider \
  --url https://token.actions.githubusercontent.com \
  --client-id-list sts.amazonaws.com

    You should see: an ARN ending in oidc-provider/token.actions.githubusercontent.com. If it says it already exists, that is fine — move on.

    If your CLI demands a thumbprint: add --thumbprint-list 6938fd4d98bab03faadb97b34396831e3780aea1. AWS no longer verifies it for GitHub, but older CLIs still require the flag.

  5. Write the trust policy — the single most important file

    This decides who may assume the role. Get the sub line wrong and either nothing works, or far too much does.

    cat > trust.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::${ACCOUNT_ID}:oidc-provider/token.actions.githubusercontent.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
        "token.actions.githubusercontent.com:sub": "repo:YOUR-USERNAME/YOUR-REPO:environment:production"
      }
    }
  }]
}
EOF

cat trust.json            # READ IT. Check the username and repo name.

    You should see: your real 12-digit account ID, your real GitHub username, and the word production.

    Why environment:production and not a branch? Because the deploy job declares environment: production, GitHub changes the subject claim to the environment form. Copying :ref:refs/heads/master from a tutorial is the #1 reason this fails. Never use * here — that would let any repository on GitHub into your account.

  6. Write the permissions policy

    What the role may actually do. Push to one ECR repo, describe one cluster. Nothing else.

    cat > permissions.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": "ecr:GetAuthorizationToken", "Resource": "*" },
    { "Effect": "Allow",
      "Action": [
        "ecr:BatchCheckLayerAvailability", "ecr:InitiateLayerUpload",
        "ecr:UploadLayerPart", "ecr:CompleteLayerUpload",
        "ecr:PutImage", "ecr:BatchGetImage"
      ],
      "Resource": "arn:aws:ecr:ap-south-1:${ACCOUNT_ID}:repository/ai-interview-dev-platform/frontend" },
    { "Effect": "Allow", "Action": "eks:DescribeCluster",
      "Resource": "arn:aws:eks:ap-south-1:${ACCOUNT_ID}:cluster/ai-interview" }
  ]
}
EOF

    You should see: no "*" anywhere except on GetAuthorizationToken, which cannot be scoped.

  7. Create the role and attach the policy

    Now the two files become a real IAM role.

    aws iam create-role \
  --role-name gh-deploy-frontend \
  --assume-role-policy-document file://trust.json

aws iam put-role-policy \
  --role-name gh-deploy-frontend \
  --policy-name deploy-permissions \
  --policy-document file://permissions.json

# copy this ARN — you need it in step 3.3
aws iam get-role --role-name gh-deploy-frontend --query Role.Arn --output text

    You should see: arn:aws:iam::<your-id>:role/gh-deploy-frontend. Save it somewhere.

  8. Let the role into the cluster

    AWS permission and Kubernetes permission are two separate systems. The role can now find the cluster; this lets it use the cluster — in one namespace only.

    aws eks create-access-entry \
  --cluster-name ai-interview --region ap-south-1 \
  --principal-arn arn:aws:iam::${ACCOUNT_ID}:role/gh-deploy-frontend \
  --type STANDARD

aws eks associate-access-policy \
  --cluster-name ai-interview --region ap-south-1 \
  --principal-arn arn:aws:iam::${ACCOUNT_ID}:role/gh-deploy-frontend \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSAdminPolicy \
  --access-scope type=namespace,namespaces=demo

    You should see: aws eks list-access-entries --cluster-name ai-interview now lists your role.

    Housekeeping: delete trust.json and permissions.json when you're done, or at least never commit them. They aren't secret, but they don't belong in the repo.

PART 3

Wire up GitHub

20 min

Two secrets, one environment, and a few values in ci.yml that must match what you just built. Notice that neither secret is an AWS credential.

  1. Create a SonarCloud project and get a token

    SonarCloud is free for public repos. Sign in with GitHub, add your repository, and choose "With GitHub Actions" as the analysis method.

    # sonarcloud.io → My Account → Security → Generate Token
# Note down: organization key and project key

    You should see: a token starting with squ_ or similar. Copy it now — it is shown only once.

  2. Create the production environment

    The deploy job references it. It also decides the sub claim you already put in the trust policy — so the name must be exactly production.

    # GitHub → Settings → Environments → New environment
# Name: production
# Optional: add yourself as a required reviewer to practise approvals

    You should see: production listed under Environments.

  3. Add AWS_DEPLOY_ROLE_ARN to that environment

    The role ARN from step 2.7. Knowing it grants nothing — a caller still needs a token the trust policy accepts.

    # Settings → Environments → production → Add environment secret
# Name:  AWS_DEPLOY_ROLE_ARN
# Value: arn:aws:iam::<ACCOUNT_ID>:role/gh-deploy-frontend

    You should see: one secret listed under the production environment.

  4. Add SONAR_TOKEN as a repository secret

    The app job needs it, and that job has no environment — so this one goes at repository level, not environment level.

    # Settings → Secrets and variables → Actions → New repository secret
# Name: SONAR_TOKEN

    You should see: SONAR_TOKEN under repository secrets and AWS_DEPLOY_ROLE_ARN under the environment. Two different places — that is correct.

  5. Make the config in the repo match your AWS

    The workflow ships with someone else's cluster names. Change them, and check the branch condition.

    # .github/workflows/ci.yml
env:
  AWS_REGION:    ap-south-1
  EKS_CLUSTER:   ai-interview
  K8S_NAMESPACE: demo
  ECR_REPO:      ai-interview-dev-platform

# sonar-project.properties
sonar.projectKey=<your key>
sonar.organization=<your org>

    Check your branch name. The deploy job only runs when the ref is refs/heads/master. If your default branch is main, every check will pass and the deploy will be skipped with no error at all. Either rename the branch or edit the if: condition.

    You should see: your changes committed and pushed.

PART 4

Run the pipeline

15 min

  1. Trigger it by hand the first time

    A manual run does exactly what a push does, but on your schedule — and the "Check config" step tells you within seconds if a secret is missing.

    # GitHub → Actions → "CI/CD frontend" → Run workflow → Branch: master

    You should see: four jobs appear — app, secrets, manifests running together, deploy waiting.

  2. Watch the three checks and read one log properly

    Do not just watch for green. Open the app job and actually read the lint, test and coverage output — that habit is what separates people who can debug pipelines from people who re-run them hoping.

    You should see: three green ticks in roughly 2–4 minutes, then deploy starting.

  3. Watch the deploy job, step by step

    These are the steps that touch your AWS account. Expand "Log in to AWS" and notice there is no key in the log — only a role being assumed.

    # the order you will see:
Check config → Log in to AWS → Log in to ECR → Build
→ Scan the image (Trivy) → Push → Get cluster credentials
→ Deploy → Verify → Show what is running → Summary

    You should see: the run summary table at the bottom with your commit SHA, the image URI, the cluster and the namespace.

  4. Prove it from your own terminal

    Trust the cluster, not the green tick.

    kubectl get pods -n demo -l app=frontend
kubectl get deploy frontend -n demo \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'

# open it in your browser:
kubectl port-forward -n demo svc/frontend 8081:80
# → http://localhost:8081

    You should see: a pod Running 1/1, an image tag equal to your commit SHA, and the login page at localhost:8081.

    Login will fail with "the server returned a web page instead of data". Correct — there is no backend and no Ingress routing /api yet. The frontend itself is working.

PART 5

Break it on purpose

40 min

This is the part most people skip and the part that actually teaches you something. A gate you have never seen fire is a gate you don't believe in. Do each one on a throwaway branch, then undo it.

  1. Experiment 1 — commit a fake AWS key

    See Gitleaks catch it, then learn why deleting the line does not fix it.

    git checkout -b break/secret
echo 'aws_access_key_id = AKIAQ7XZ4T2WV9LMN3BC' > creds.txt
echo 'aws_secret_access_key = wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY' >> creds.txt
git add creds.txt && git commit -m "oops" && git push -u origin break/secret

    You should see: the secrets job go red, naming the file and line.

    Now the real lesson: delete the file, commit, push again — it is still red, because the old commit still holds the key. In real life you rotate the credential first; rewriting history second. Just delete the branch when you're done.

  2. Experiment 2 — add one unused variable

    Proves that --max-warnings 0 really does mean zero.

    git checkout -b break/lint
# add this line inside any component in src/pages/
#   const unusedThing = 42;
git commit -am "add a warning" && git push -u origin break/lint

    You should see: the app job fail at the Lint step — on a warning, not an error.

  3. Experiment 3 — break the trust policy

    This produces the error you are most likely to hit for real. Meet it now, on purpose, when you already know the cause.

    # edit trust.json: change the sub to the branch form
#   "…:sub": "repo:YOU/YOUR-REPO:ref:refs/heads/master"

aws iam update-assume-role-policy \
  --role-name gh-deploy-frontend --policy-document file://trust.json

# now run the workflow again from the Actions tab

    You should see: the deploy job fail at "Log in to AWS" with Not authorized to perform sts:AssumeRoleWithWebIdentity.

    Put it back to the environment:production form and re-run. Same command, correct file.

  4. Experiment 4 — ship a pod that never becomes ready

    The best one. You will watch an automatic rollback save a live site.

    # k8s/deployment.yaml → readinessProbe → path: /not-here
git commit -am "break the readiness probe"
git push origin master

    You should see: Deploy hangs, fails after the 5-minute timeout, then the "Roll back" step runs rollout undo — and kubectl get pods -n demo shows the old pod still healthy the whole time.

    That is the point. A broken deploy did not become a broken website. Revert the change and push again.

  5. Experiment 5 — ship a vulnerable base image

    Shows that Trivy blocks the image before it reaches ECR.

    # Dockerfile → change the runtime stage to an old tag, e.g.
#   FROM nginx:1.21-alpine AS runtime
git checkout -b break/cve && git commit -am "old base" && git push -u origin break/cve
# then run the workflow on that branch and temporarily flip the deploy `if:`

    You should see: the Trivy step print a table of CVEs and fail the job. Check ECR — the image was never pushed.

    If nothing critical shows up: temporarily set severity: HIGH,CRITICAL in the Trivy step. Then put everything back.

PART 6

Clean up — do not skip this

15 min
This is the step that costs students money

An EKS cluster bills whether you use it or not. Forgetting it over a two-week semester break is a bill of roughly $70. Set a phone reminder before you start Part 2 if you have to.

WhatRough costNotes
EKS control plane$0.10 / hrcharged even with zero pods running
2 × t3.small nodes~$0.05 / hrthe worker machines
NAT gateway~$0.06 / hravoided by --vpc-nat-mode Disable in step 2.2
EBS volumes~$0.01 / hrnode disks
ECR storagepennies$0.10 per GB-month
Total~$0.20 / hrabout $5 a day, $145 a month

  1. Delete the cluster

    This is 95% of the bill. It takes 10–15 minutes; wait for it to finish.

    eksctl delete cluster --name ai-interview --region ap-south-1 --wait

    You should see: "all cluster resources were deleted".

  2. Delete the ECR repository

    --force because it still contains your images.

    aws ecr delete-repository \
  --repository-name ai-interview-dev-platform/frontend \
  --region ap-south-1 --force

    You should see: the repository echoed back in the JSON response.

  3. Delete the IAM role

    Free, but leaving an unused role that can reach your account is exactly the habit this project is teaching you to avoid.

    aws iam delete-role-policy --role-name gh-deploy-frontend --policy-name deploy-permissions
aws iam delete-role --role-name gh-deploy-frontend

    You should see: no output. That means success.

  4. Delete the GitHub OIDC provider — only if nothing else uses it

    It is free and shared account-wide. If you plan to build a second pipeline, keep it.

    aws iam delete-open-id-connect-provider \
  --open-id-connect-provider-arn \
  arn:aws:iam::${ACCOUNT_ID}:oidc-provider/token.actions.githubusercontent.com

    You should see: no output.

  5. Check nothing survived

    Deletions occasionally leave orphans, especially load balancers and disks. Look with your own eyes.

    aws eks list-clusters --region ap-south-1
aws ec2 describe-instances --region ap-south-1 \
  --filters "Name=instance-state-name,Values=running" \
  --query "Reservations[].Instances[].InstanceId"
aws elbv2 describe-load-balancers --region ap-south-1 --query "LoadBalancers[].LoadBalancerName"
aws ec2 describe-volumes --region ap-south-1 --query "Volumes[?State=='available'].VolumeId"

    You should see: empty lists from all four. Then open the AWS Billing console tomorrow and confirm the daily cost has dropped to near zero.

CHECK

Did you actually understand it?

10 min

Answer out loud before opening each one. If you can answer all eight, you can explain this project in an interview.

Where is the AWS access key stored in this project?

Nowhere. There isn't one. GitHub sends a short-lived signed token, AWS checks it against the trust policy and returns credentials that expire within the hour. The only AWS credentials that exist are the ones on your own laptop, used to build the infrastructure in Part 2.

What does id-token: write allow?

Only that the job may ask GitHub for an identity token. It grants no AWS access at all. Whether that token is worth anything is decided entirely by the trust policy on the AWS side.

Why is the image tagged with the commit SHA instead of latest?

So you can look at any running pod, read its tag, and go straight to the exact line of code. With latest, two pods can be running different code under the same name and rollback becomes guesswork.

Why does Trivy run before the push and not after?

Because a vulnerable image that never reaches the registry cannot be pulled by anyone later. Scanning after the push means the bad image is already sitting there for someone to deploy.

Why isn't the API URL baked into the JavaScript bundle?

Because then you would need one image per environment, and the image you tested in dev would not be the image you ship to production. Instead the entrypoint writes runtime-config.js at container start, so one image behaves differently in each namespace.

What is the difference between the liveness and readiness probes?

Liveness asks "is it alive?" — if it fails, the container is restarted. Readiness asks "can it serve traffic?" — if it fails, the pod is removed from the Service but keeps running. Readiness is what makes a zero-downtime rollout possible.

Your deploy fails with "Not authorized to perform sts:AssumeRoleWithWebIdentity". First thing you check?

The sub condition in the trust policy. Because the deploy job declares environment: production, it must be repo:OWNER/REPO:environment:production — not the ref:refs/heads/master form most tutorials show.

Why does deleting a leaked secret from a file not fix a Gitleaks failure?

Git keeps every version of every file forever, and Gitleaks scans the whole history. More importantly, the secret has already been published — so the real fix is to rotate the credential. Rewriting history only makes the scanner quiet.
